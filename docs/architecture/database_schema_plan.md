# CareerProof AI Database Schema Plan

This document plans the PostgreSQL/Supabase schema for the student MVP. It is a planning artifact only; it does not define executable migrations.

## Design Assumptions

- Supabase Auth is the identity provider.
- `public.users.id` mirrors `auth.users.id` and is the application-owned profile root.
- Student data is private by default and only visible to the owning authenticated user.
- Server-side AI parsing, matching, and generation jobs may use service-role access, but service keys must never be exposed to client code.
- All MVP tables should live in `public` unless a later migration introduces private schemas for privileged functions or internal job state.
- Use `uuid` primary keys generated by `gen_random_uuid()` for application tables, except `users.id`, which should match `auth.users.id`.
- Use `timestamptz` for all timestamps.
- Use `jsonb` where AI/parser output needs schema flexibility, then normalize high-value fields into first-class columns over time.

## MVP Relationship Diagram

```text
auth.users
  1:1 public.users
    1:1 student_profiles
    1:N resumes
      1:1 parsed_resume_data
      1:N skill_evidence
    1:N skills
      1:N skill_evidence
    1:N job_matches
      N:1 jobs
      1:N generated_materials
      1:1 applications
    1:N project_suggestions
    1:N audit_logs

jobs
  1:N job_matches

applications
  N:1 jobs
  N:1 resumes
  N:1 generated_materials
```

## Table Plans

### users

**Purpose:** Application-owned user record linked to Supabase Auth. Keeps role, onboarding state, and account-level metadata outside unsafe user-editable auth metadata.

**Columns:**

| Column | Data type | Notes |
| --- | --- | --- |
| `id` | `uuid` | Same value as `auth.users.id`; primary key. |
| `email` | `citext` | Cached email for display/search; source of truth remains Supabase Auth. |
| `role` | `text` | MVP default `student`; future values: `recruiter`, `university_admin`, `admin`. |
| `status` | `text` | `active`, `disabled`, `pending_deletion`. |
| `onboarding_completed_at` | `timestamptz` | Null until first onboarding is complete. |
| `last_seen_at` | `timestamptz` | Updated by app activity. |
| `created_at` | `timestamptz` | Default now. |
| `updated_at` | `timestamptz` | Updated by trigger. |

**Primary key:** `id`

**Foreign keys:** `id` references `auth.users(id)` on delete cascade.

**Indexes:**

- Unique index on `email`.
- Index on `role`.
- Index on `status`.
- Index on `created_at`.

**RLS notes:**

- Enable RLS.
- Students can select and update their own non-privileged account row where `id = auth.uid()`.
- Users must not update `role` or `status` from client-side code.
- Admin/service-only policies should manage role/status changes.
- Do not authorize from `raw_user_meta_data`; use this table or app metadata for authorization.

**Future recruiter/university expansion:**

- Add organization membership tables rather than overloading `users`.
- Keep `role` as a coarse account type; model recruiter teams and university programs with separate join tables.
- Add `terms_accepted_at`, `privacy_region`, and `data_retention_tier` if institutional contracts require them.

## RLS Policy Recommendations

- Enable RLS on every table in `public`.
- Use ownership policies based on `(select auth.uid()) = user_id` or `(select auth.uid()) = id` for `users`.
- For updates, define both `using` and `with check` conditions; PostgreSQL UPDATE requires row visibility before the update can succeed.
- Keep service-role writes for parser/matcher/generator fields that students should not forge, such as `match_score`, `parser_version`, and AI model metadata.
- Avoid JWT `user_metadata` for authorization. If JWT claims are needed, use trusted app metadata and account for token freshness.
- Add ownership consistency checks for tables with multiple user-linked foreign keys. For example, `skill_evidence.user_id`, `skill_id`, and `resume_id` should all belong to the same user.
- Prefer explicit policies per operation instead of broad `all` policies.
- Treat jobs carefully:
  - Shared catalog jobs can be readable by authenticated users.
  - User-created private jobs should be readable only by the creator.
  - A future organization-owned jobs model should use organization membership policies.
- Keep privileged functions out of exposed schemas when later implementing server-side helpers.
- Add admin/reviewer policies only after the role and organization model exists.

## Storage Bucket Plan For Resumes

**Bucket:** `resumes`

**Bucket type:** Private file bucket.

**Path convention:**

```text
{user_id}/{resume_id}/original.{ext}
{user_id}/{resume_id}/normalized.txt
{user_id}/{resume_id}/preview.{ext}
```

**Metadata stored in database:** `resumes.storage_bucket`, `resumes.storage_path`, `original_filename`, `content_type`, `file_size_bytes`, and `checksum_sha256`.

**Allowed MVP file types:**

- PDF: `application/pdf`
- DOCX: `application/vnd.openxmlformats-officedocument.wordprocessingml.document`
- Optional later: plain text for imports.

**Recommended limits:**

- Start with a conservative file size limit such as 5-10 MB.
- Validate content type and extension server-side before creating parse jobs.
- Keep extracted text in `parsed_resume_data.raw_text`; keep original files in Storage.

**Storage RLS policy shape:**

- Authenticated users can select objects in the `resumes` bucket only when the first path segment equals their `auth.uid()`.
- Authenticated users can insert objects only into their own `{user_id}/...` folder.
- Authenticated users can delete only their own objects if product deletion is supported.
- Upsert/replace requires select and update permissions in addition to insert; avoid upsert in MVP unless replacement behavior is explicitly designed.
- Parser/service role can read objects for processing and write derived parser artifacts.
